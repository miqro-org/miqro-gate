# ADR-0028：门户用户自助 MCP 凭据形态（自助接入面）

- 日期：2026-10-14
- 状态：**Accepted（2026-10-14）**——所有者已拍板**选项 A（每用户一个消费者）**；落地清单与验收跟踪见 issue #30。
- 效力：**本文为实施依据**。这是新增决策，**不修订** ADR-0010 / ADR-0011 定义的两条消费者通道——门户消费者沿用同一凭据形态，只是新增了「归属」与自助面。
- 关联：issue #1（自助接入面，本文的触发者）；#25 / #26 / #27（作用域口径统一与「创建即可选作用域」，PR #28）；issue #23 + PR #24（服务登记与排错：`operations-runbook.md` §3f）；[ADR-0010](0010-consumer-api-key-billing.md)（消费者 API Key，Accepted）；[ADR-0011](0011-consumer-jwt-authentication.md)（消费者 JWT，Accepted）；[ADR-0013](0013-mcp-proxy-wiring-proposal.md)（MCP 调用代理接线，Accepted）；`docs/api-contract.md` §5.10；上游侧 `docs/gateway-integration.md`（MCP 仓库）。
- 触发事件：issue #1——桌面端与门户用户要经网关调 MCP，就需要**每人一把自己的凭据**；而当前 `api_consumers` 与 `users` **之间没有任何关联列**，`/api/v1/me/*` 下也没有 MCP 相关端点。凭据形态不定，自助面无法开工。

---

## 1. 现状

### 1.1 今天用户是怎么拿到 MCP 凭据的

管理员在「API 消费者」页建一个消费者（`POST /api/v1/admin/api-consumers`），把 `mqk_api_…` 交给使用者。四个后果（issue #1 的原话：**缺的不是网关能做什么，而是普通用户和桌面客户端够不着它**）：

| 问题 | 具体表现 |
|---|---|
| 凭据共享 | 一把 Key 发给多人，日志里只有同一个消费者名——**看不出是谁调的**，也无法按人吊销 |
| 不透明 | 调用虽经网关（有 ACL / 访问日志），但**归因到消费者**而非用户；没有消费者维度的用量也谈不上按人 |
| 用户看不到 | 「MCP 服务」页、访问日志页都是**管理面**页面；用户登录后看不到「我能用哪些服务、地址是什么、凭据是什么」 |
| 客户端内置 | 桌面端现状是内置一个共享 token（明文硬编码），换人/离职只能整体换 |

### 1.2 已有的两块地基（本文不重新讨论它们）

- **ADR-0010**：消费者 API Key（`mqk_api_…`；库中只存 HMAC 摘要，明文仅创建时展示一次）。
- **ADR-0011**：消费者 JWT（**外部系统自签** Token，网关只存公钥验签，`sub` → 消费者名）。
- 两条通道都接进 MCP 数据面（ADR-0013），都受 `mcp:call` 作用域与**工具级 ACL** 约束——作用域口径已于 #25/#26 统一（未设 = 全权限，最小权限必须显式声明），创建路径已支持**创建即可选作用域**（#27 / PR #28）。

**注意**：这两篇解决的是「**外部系统怎么认证**」，都**没有**回答「门户用户如何自助取得凭据」——这正是本文要补的一格。

### 1.3 缺的是什么

1. **用户 ↔ 凭据的映射**：`api_consumers` 的列是 `id / tenant_id / name / key_digest / key_prefix / status / version / created_at / updated_at / jwt_* / capabilities / expires_at`——没有指向 `users` 的任何字段。
2. **自助端点**：`/api/v1/me/*` 下没有任何 MCP 端点（`GET /me/virtual-keys`、`/me/grants` 等是推理面的）。
3. **「有权使用」的口径**：今天 `mcp_access_grants` 是按**消费者**授权的；要回答「**这个用户**有权用哪些服务/工具」，必须先定映射。

## 2. 决策点

一句话：**用户自助拿到的那个凭据，是什么形态、以及它和用户如何绑定。**

## 3. 选项

### A. 每用户一个消费者（给 `api_consumers` 加归属列）

用户首次自助取凭据时，为其创建一个「门户消费者」（`owner_user_id = 该用户`，同租户同用户唯一），把 Key 一次性展示给本人；此后该用户看到的服务列表按**他的消费者**的 ACL 口径过滤。

- 表结构：`api_consumers` 加可空列 `owner_user_id`（+ 部分唯一索引：同租户同用户至多一条「门户消费者」）；存量外部系统消费者保持 `NULL`。
- 签发/验签：沿用 ADR-0010（HMAC 摘要）——无新密码学链路。
- 吊销/轮换：禁用/重建该消费者 = 按人吊销；轮换即重发 Key（一次性展示）。
- 审计与归因：现有 `mcp_access_log.consumer_name` 天然变成「人名（或用户绑定名）」，无需改日志模型。

### B. 用户维度 JWT（门户签发、网关验签）

门户为自己的登录用户签 JWT（`sub` = 用户标识），网关侧配公钥验签。

- 表结构：无需新列（但需要一个用户级公钥/密钥的管理位，或复用平台密钥体系）。
- 签发/验签：**新建**签发与轮换链路；签名密钥的保管、有效期与吊销都要新设计。
- 语义风险：ADR-0011 的 JWT 是「**外部平台自签**、网关只验签」，若再加一条「门户自签」，同一通道出现两种信任来源，排障时难以区分。
- 审计与归因：JWT 只带 `sub`，`mcp_access_log` 的消费者名需要额外映射或改模型。

### 对比

| 维度 | A：每用户一个消费者 | B：用户维度 JWT |
|---|---|---|
| 新表结构 | 一列 + 一个部分唯一索引（可空，向后兼容） | 无列变化，但需用户级密钥管理位 |
| 新密码学链路 | 无（复用 ADR-0010） | 有（签发、轮换、吊销、时钟/有效期） |
| 与现有 ACL 的契合 | **天然**：grants 本来就按消费者 | 需把「用户 → 消费者/工具」再映射一层 |
| 按人吊销 | 禁用消费者即可 | 需要 JWT 黑名单或短有效期 + 刷新 |
| 审计归因 | 现成（consumer_name） | 需要额外映射 |
| 桌面端要做的 | 拿一个 Key（与今天同形） | 接一条取 JWT 的流程（含刷新） |
| 与 ADR-0011 的关系 | 并行不冲突（外部系统 vs 门户用户） | 混入同一通道，语义变浑 |
| 主要风险 | 用户可自助看到/轮换自己的 Key，UX 与泄漏面要设计 | 密钥体系与信任源增多 |

## 4. 选定：A（每用户一个消费者，2026-10-14 拍板）

理由：与 ADR-0010 / ADR-0013 的既有形态一致；**与「按消费者授权」的现有 ACL 天然对齐**（不用再造一层映射）；「按人吊销」直接落在既有的 disable 语义上；桌面端只需拿一个 Key（改连成本最小）；不引入新的密码学与密钥保管负担。

实施期的四项设计约束（落地时必须满足，跟踪见 issue #30）：

1. **命名与可辨识**：门户消费者建议用可辨识的命名（如 `<用户名>@portal`）或加 `kind` 标识，让管理端能一眼区分「人的凭据」与「外部系统的凭据」。
2. **一个用户是否允许多把**：默认一把（自助轮换就是重发），若将来要「一设备一把」，加列语义要能扩展。
3. **泄漏与可见性**：Key 一律只展示一次；「我的凭据」页提供轮换与撤销；是否需要管理员可见（建议：管理员可见元数据、不可见明文）。
4. **与推理面 Key 的关系**：推理面用的是 Virtual Key（`mqk_live_…`，绑定项目/产品/凭证），而 MCP 面用的是消费者凭据（`mqk_api_…`）——两者用途不同，自助面**不合并**它们，界面要讲清区别。

## 5. 落地清单（已拍板；跟踪 issue #30）

- **迁移**：新增可空列 + 部分唯一索引（Flyway 追加，不改既有迁移）；存量消费者不受影响。
- **接口**：`GET /api/v1/me/mcp-services`（有权使用的服务 + 该服务下**对本人可见**的工具 + 接入地址与凭据形态提示，口径与 ACL 一致：无权的服务不出现、越权查询不泄露服务名）；自助凭据端点（首次签发 / 查看元数据 / 轮换 / 撤销）。
- **ACL 口径**：明确「用户有权使用」= 其门户消费者在 `mcp_access_grants` / 服务级名单里的状态；管理员放开或收窄某服务/工具后，用户列表随之变化。
- **失效可感知**：凭据被禁用/轮换、服务下线、会话回收要能区分（issue #1 的验收之一）。
- **桌面端**：改为登录用户自己的凭据，删除内置共享 token（由桌面端跟进）。
- **文档**：`api-contract.md` 新增 `/me/mcp-services` 一节；`client-onboarding.md` §4 与 `operations-runbook.md` §3c 中「凭据需管理员创建」的措辞改为自助 + 管理员兜底。

## 6. 与其它未决项的关系（本文不解决）

- **MCP 用量与计费口径**：ADR-0013 决策点 3 仍为「维持未定」，需要 owner 先拍板；本文不触及。
- **上游身份透传**（网关向上游注入身份头 + 信任模型）：与本文正交；若要做需另开 ADR（旧仓库曾以同名 ADR 提过，**未迁入本仓库**，现为空白）。
- **自助面是否走申请制**（用户申请、管理员批准）：本文默认**直接发放**（与「普通用户免审批创建自己的 Virtual Key」的既有边界一致）；申请制可作为后续独立议题。
- **服务级开放 vs 逐人授权**：若某服务「人人可用」，管理员可在服务级放开、只在工具级收窄——**凭据仍按人发放**，本文的「按人可追踪」不受影响。

## 7. 拍板结果（2026-10-14）

**选定 A：每用户一个消费者。** 落地清单见 issue #30（Flyway 归属列 + `/api/v1/me/mcp-services` + 自助签发/轮换/撤销 + ACL 口径 + 文档同步；桌面端删除内置 token 由桌面端仓库跟进）。

未采纳的两条留档备查：

- **B（用户维度 JWT）**：实施前需先补一份「门户签发 JWT」的密钥与信任模型设计（含与 ADR-0011 外部自签的区分方式）。
- **暂不做（维持管理员发放）**：等价于维持现状——凭据共享、看不出谁调的，桌面端也删不掉内置 token。
