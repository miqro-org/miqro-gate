# ADR-0029：认证端点的暴力破解防护策略——锁定封顶、计数衰减与是否引入按来源限流

- 日期：2026-10-13
- 状态：**Proposed（待所有者拍板）**——本文只做选项与代价留档，**拍板前不实现**。拍板后二选一收口：选择调整 → 本文转 Accepted 并按下节「建议实施顺序」立项；选择维持现状 → 本文转 Accepted，结论 = 维持，并把 §1.3 的可触发锁定记为**已接受风险**（避免下次再被当新发现重开）。
- 效力：**无**。Proposed 不修订任何产品决策。**若采纳「按来源限流」的任一变体，须先修订 `CLAUDE.md §2`「不限流、不因预算阻断，只做 Webhook 告警」并新增 ADR**（先例：ADR-0020 对同一句的修订）；若限流只覆盖认证端点、不触及推理数据面，则 §2 不受影响——论证见 §3.2。相关既有评估见 [ADR-0026](0026-rate-limiting-evaluation.md)（速率限流，Proposed，A/B/C 未拍板）。
- 关联：`CLAUDE.md §2`（不限流）、[ADR-0026](0026-rate-limiting-evaluation.md)（速率限流评估）、[ADR-0020](0020-quota-soft-landing.md)（阻断 vs 不阻断的同类取舍先例）、[ADR-0015](0015-open-admin-api-machine-credentials.md)（机器凭证面另有一套，不受本文影响）、`docs/security.md:43`（「登录失败指数延迟和**临时**锁定」，本文的直接起点）、`docs/security.md:65`（门户 IP 白名单 F05，已实现——本文 §3 讨论的是它没覆盖的形态）。
- 触发事件：审查认证端点防护时发现三条并列问题——(a) 全仓无任何按来源的请求限流；(b) 账号锁定可被**未认证攻击者**在已知用户名上近乎无限延长（§1.3）；(c) 开放注册默认开启且注册接口以 `409 USERNAME_TAKEN` 可枚举用户名，与登录侧刻意做到的防枚举相矛盾。其中 (b) 与 `security.md` 声明的「临时锁定」直接冲突。

---

## 1. 现状

### 1.1 已有的三道防线

| 机制 | 位置 | 作用 |
|---|---|---|
| 渐进延迟 | `AuthenticationService.progressiveDelay(estimatedFailCount)`（`:164`） | 每次失败后请求内延迟递增 |
| 账号锁定 | `AuthenticationService.recordFailedLogin`（`:220-252`） | 失败数 ≥ 阈值后置 `LOCKED` + `lockedUntil` |
| 时序不可区分 | `login`（`:148-163`） | 未知用户 / DISABLED / LOCKED 都做同一份 Argon2 假校验，统一 401，防枚举 |

配置默认值：`loginMaxFailures = 5`、`loginLockBase = 1 min`（`AuthProperties.java:24-27`）；`application.yml` 未覆盖。

> 登录侧为防枚举做得相当细：`estimatedFailCount` 对未知用户名从 2 起算，就是为了让"不存在的账号"和"错密码的已知账号"观察到相同延迟（`:156-160`）。

### 1.2 没有的：任何按来源（IP）的限流

全仓无 `RateLimiter` / `bucket4j` / `resilience4j` 之类实现（命中的 `rate` 都是错误率、告警指标）。`AdminIpAllowlistFilter`（F05）是**静态 CIDR 白名单**，不是速率控制，且只作用于门户面。因此认证端点对单一来源的请求速率没有任何约束——`loginMaxFailures` 限制的是**每个用户名**的失败数，不是每个来源的请求数。

### 1.3 核心问题：锁定按用户名计，而它由攻击者触发

`recordFailedLogin` 内的时长计算（`:231-235`）：

```java
long multiplier = 1L << Math.max(0, newFailCount - authProperties.getLoginMaxFailures());
Duration lockDuration = authProperties.getLoginLockBase().multipliedBy(Math.min(multiplier, 1024));
lockedUntil = now.plus(lockDuration);
```

倍率随**累计失败数**指数增长，封顶 1024 倍 → `1 min × 1024 = 1024 min ≈ 17.1 小时`。

关键点：**`login` 对已锁定账号同样调用 `recordFailedLogin`**（`:166-173`——密码不校验、走假校验把 `passwordValid` 置 false，然后无条件进失败分支）。于是每一次针对已锁定账号的尝试都会把 `lockedUntil` 重置为 `now + lockDuration`。

推算（默认配置）：

| 第几次失败 | 倍率 | 锁定 |
|---|---|---|
| 5 | 2⁰ = 1 | 1 min |
| 6 | 2¹ = 2 | 2 min |
| … | … | … |
| 15 | 2¹⁰ = 1024 | ≈ 17.1 h |
| ≥16 | 封顶 1024 | ≈ 17.1 h（每次从此刻重算） |

因为第 6 次及以后都发生在锁定期内、且每次立即重设截止时间，**攻击者不需要等待**：约 11 个快速请求即可爬到上限，此后**每 17.1 小时发一个请求**就能让该账号永久无法登录。代价对攻击者可忽略，代价对受害者是完全不可用。

这与 `docs/security.md:43` 声明的「**临时**锁定」不符——受害者无法通过等待恢复，恢复与否由攻击者决定。

同时注意这条与 (c) 的耦合：能触发锁定的前提是**知道用户名**，而 (c) 恰好提供了枚举通道。

## 2. 决策点 1：锁定时长是否封顶 / 失败计数是否衰减

问题：怎样让「锁定」真的临时，同时不把暴力破解抵抗力削太多。**这两个目标天然对立**——锁定越长越抗爆破，也越容易被用来做 DoS。

| 选项 | 说明 | 抗爆破 | 抗 DoS |
|---|---|---|---|
| **A. 维持现状** | 不封顶，每次失败都重设截止时间 | 强 | **无**（§1.3） |
| **B. 锁定总时长封顶** | 新增 `loginLockMax`（建议默认 15 min ~ 1 h）；`lockDuration = min(base × multiplier, max)`；且**已处于锁定期内不推进截止时间** | 中（上限内仍指数增长） | 强（受害者最长停机 = 一个 max 窗口） |
| **C. 失败计数衰减** | 锁定到期时（或距上次失败超过某窗口时）把 `failedLoginCount` 归零 | 中（每个破解周期须重新爬 5 次阈值） | 中（攻击者每周期成本 = 阈值次请求） |
| **D. B + C** | 封顶 + 衰减 | 中 | 强 |

**推荐 D**。理由：B 单独用时，攻击者仍可在每个 max 窗口末尾打一发保持锁定（成本 ≈ 1 请求/max 窗口）；叠加 C 后，每个周期还必须重新爬满阈值，成本抬到 ~5 请求/周期。两者都让「临时」重新成立，而不至于把记忆中的攻击难度降到无意义——**默认值仍可按部署调整**，这正是把它做成配置项而不是硬编码的理由。

**残余缺口（写在这里备查）**：D 之后，攻击者仍能以约 `maxFailures / loginLockMax` 的请求速率让你的账号持续不可用。**锁定机制本质上无法区分"攻击者在打"和"用户忘了密码"**，所以真正的下限由决策点 2 决定。

## 3. 决策点 2：是否引入按来源限流

### 3.1 选项

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. 不做** | 只靠决策点 1 收紧 | §2 的残余缺口保留 |
| **B. 只覆盖认证端点** | 对 `/api/v1/auth/{login,register}` 按来源 IP 计数（滑动窗口），超限 429 | 需要一个计数器载体（内存 / DB）；反代部署需正确取客户端地址——`AdminIpAllowlistFilter.effectiveClientAddress`（`#445`，从右遍历 XFF、只信受信代理）已经解决了这个取址问题，可直接复用 |
| **C. 全站（含推理数据面）** | TPM/RPM 类限流 | **触及 `CLAUDE.md §2`「不限流」**，须先改该决策 + 新增 ADR；且与 ADR-0026 尚未拍板的 A/B/C 是同一议题 |

### 3.2 为什么 B 不触 §2

`CLAUDE.md §2` 的原文是「**不限流、不因预算阻断，只做 Webhook 告警**」，其语境是**推理数据面**——同一节其余条目谈的是 Virtual Key、跨供应商路由、缓存、用量保存等数据面语义；ADR-0026 也把该条解释为"不做模型请求的速率治理"。

认证端点不是模型流量：它没有"额度"语义，也不存在"长任务瞬时强度就是正常工作形态"这类顾虑（ADR-0026 §2.1 反对限流的核心理由）。因此**对认证端点做按来源的暴力破解防护，与 §2 属于不同议题**。但本文不替 owner 断言这一点——**若 owner 认为 §2 覆盖全部入站路径，则 B 也须先改该条并新增 ADR**，请在拍板时一并明确。

### 3.3 B 的一个现成抓手

F05 已经建立了「受信代理 + 从右遍历 XFF」的取址规则并写在 `AdminIpAllowlistFilter` 里。B 若实施，**必须复用同一个取址函数**，否则会出现"IP 白名单看到的地址"与"限流计数的地址"不一致——那本身就是一类绕过。为避免复制逻辑，建议把 `effectiveClientAddress` 提取为共享工具（与 `RequestPaths` 的定位一致：安全判定只从一个地方读输入）。

## 4. 决策点 3：开放注册的默认值与用户名枚举

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. 保持** | `registrationEnabled` 默认 true（`application.yml:22`，注释写明是「便于内测/试用」）；重名返回 `409 USERNAME_TAKEN`（`AuthenticationService.java:338`） | 枚举通道保留；生产环境静默开放注册 |
| **B. 生产环境 fail-fast** | `ProductionStartupValidator` 增加一条：生产模式下注册开启即拒绝启动，除非显式 opt-in——与它现有的 cookieSecure / Origin 校验同款（`ProductionStartupValidator.java:66-91`） | 改变现有部署的启动行为，需在发布说明中明示 |
| **C. 注册响应不可区分** | 重名不再返回 409 | 与「首版 50 账号的内部私有化系统」不匹配；会把一次即时校验变成异步确认路径，改动面最大 |

**推荐 B**，并把枚举压力交给决策点 2 的限流去压。C 不建议：本产品的注册是内部试用便利，不是对外开放能力。

⚠️ 需注意 B 的实现细节：`MIQROKEY_REGISTRATION_ENABLED` 的当前默认是 `true`，因此"未设置"与"显式设为 true"在配置上不可区分。B 要么引入区分（如默认改为 `false` 并让内测部署显式置 true），要么在 validator 里接受"生产必须显式配置该项"的语义。**这是 B 落地时必须先定的一步，不要留给实现者临场判断。**

## 5. 一个必须先说清的事实：最小修法不解决问题

"锁定期内不推进截止时间"这一行改动（很可能是看到 §1.3 后的第一反应）**只提高爬坡成本，不改稳态**：

- 现状：约 11 个快速请求爬到倍率上限，然后每 17.1 h 一发维持 → **≈ 11 请求 + 1 请求/17.1h**
- 只做该行改动：爬坡需要等每次锁过期才能推进倍率（成本升到数天），但**到期后打一发照样重新锁满 17.1 h** → 稳态仍是 **1 请求/17.1h**

也就是说，若只提交那一行，DoS 依然成立，只是从"11 个快请求"变成"需要耐心若干天"。**该改动本身是必要的（它让截止时间不再被锁定期内的尝试推动），但不构成解法**；上界（决策点 1-B）或衰减（1-C）才是。

> 记录这一条是为了避免一次"看起来修了、其实没修"的提交。

## 6. 建议实施顺序（Accepted 后）

1. 决策点 1：新增 `loginLockMax` 配置 + 锁定期内不推进截止时间；失败计数在锁到期时归零。
2. 决策点 3-B：`ProductionStartupValidator` 增加注册项校验（按 §4 的注意事项先定默认值语义）。
3. 决策点 2-B（若采纳）：提取共享的 `effectiveClientAddress`，在认证端点上按来源计数。
4. 文档：更新 `docs/security.md`（§43 的「临时锁定」要写出上界）、`docs/configuration-reference.md`（新配置项）、`docs/api-contract.md`（若引入 429）。
5. 测试：锁定上界（单测）；到期归零（单测）；限流的窗口与取址（单测 + 集成）；生产校验 fail-fast（`ProductionStartupValidatorTest` 已有先例）。
6. **不要**在实现中改动 `LoginFailureConcurrencyTest` 断言的「计数器等于并发尝试数」不变式——它是原子性证据，决策点 1-C 的归零发生在**锁定到期**时，与该不变式不冲突；若实现后发现冲突，说明归零的时机选错了。
